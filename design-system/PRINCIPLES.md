# Prism 디자인 원칙

Perplexity 정렬 비주얼(`DESIGN.md`) 위에 얹는 **UX·플로우 원칙**. 비주얼이 "어떻게 보이나"라면, 이 문서는 "사용자가 어떻게 흐르나"를 정한다.

> 한 줄 강령 · **각 단계는 명확하게 파악되고, 컴포넌트는 사용 순서를 따라 간결·명확·심플하다.**

---

## 0. 두 개의 상위 원칙

### A. 단계 명확성 (Step Clarity)
사용자는 언제나 **지금 어디에 있고, 무엇을 하면 되고, 다음에 뭐가 오는지** 안다. 한 화면은 한 가지 결정만 요구한다.

### B. 사용 순서 기반 간결성 (Flow-ordered Simplicity)
화면의 컴포넌트는 **시선·조작 순서대로** 배치된다. 순서를 따라가면 자연스럽게 과업이 끝난다. 순서에 기여하지 않는 요소는 뺀다.

---

## 1. 단계(Step)를 명확하게 만드는 규칙

1. **한 화면 = 한 주요 행동.** 주 CTA(Blue primary)는 화면당 하나. 나머지는 secondary/ghost로 내린다.
2. **현재 위치를 항상 표시.** 멀티스텝은 단계 라벨(`1 / 3`)이나 활성 탭으로 "여기"를 고정한다.
3. **상태를 숨기지 않는다.** 로딩·진행·완료·에러는 각각 고유한 시각 상태를 가진다(아래 6장).
4. **다음 행동을 미리 보여준다.** 빈 상태(empty)도 "무엇을 하면 되는지" 한 줄로 안내한다. 사과하지 않는다.
5. **되돌리기 가능.** 파괴적 행동 전에는 Dialog로 확인, 완료 후에는 Toast로 결과를 알린다.

```
나쁨:  [설정 12개 + 저장 + 삭제 + 내보내기]  ← 한 화면에 결정 4개
좋음:  단계1 입력 → 단계2 확인 → 단계3 완료   ← 각 단계 결정 1개
```

---

## 2. 컴포넌트 사용 순서 (Flow Order)

컴포넌트는 "갤러리 목록"이 아니라 **과업의 순서**다. Prism의 전형 흐름과 매핑:

| 순서 | 단계 | 주 컴포넌트 | 역할 |
|---|---|---|---|
| 1 | **시작** | `Input(composer)` | 사용자의 첫 입력 · 화면의 주인공, 가장 크게 |
| 2 | **범위 좁히기** | `Button(pill)` | 모드/필터 선택. 입력 바로 곁, 선택은 1개 활성 |
| 3 | **실행** | `Button(primary)` | 단 하나의 Blue CTA로 진행 |
| 4 | **진행/대기** | 상태(skeleton·streaming) | 결과가 오는 중임을 명확히 |
| 5 | **결과 읽기** | `Card(answer)` + `ds-answer` | 콘텐츠가 주인공, 68ch 리딩 폭 |
| 6 | **근거 확인** | `Card(source)` · `Badge(citation)` | 결과를 뒷받침, 절대 본문을 가리지 않음 |
| 7 | **데이터 보기** | `Table` | 정형 데이터는 조용한 표로 |
| 8 | **부가 결정** | `Dialog` | 공유·설정·업그레이드 등 흐름을 끊는 결정만 |
| - | **피드백** | `Toast`(예정) · `Badge(status)` | 결과/상태 알림 |
| - | **이동** | `Tabs(underline/sidebar)` | 단계가 아닌 "장소" 전환 |

원칙: **위에서 아래로, 왼쪽에서 오른쪽으로** 컴포넌트를 두면 사용 순서와 일치한다. 순서를 거스르는 배치(결과 위에 부가 설정)는 금지.

---

## 3. 간결·명확·심플 체크리스트

새 화면/컴포넌트를 추가하기 전 통과해야 할 질문:

- [ ] **간결** · 이 단계에서 결정은 하나인가? 뺄 수 있는 요소는 다 뺐는가?
- [ ] **명확** · 라벨만 보고 무슨 일이 일어날지 아는가? (plain verb: Ask·Search·Share)
- [ ] **심플** · variant·옵션을 새로 만들지 않고 기존 8 컴포넌트로 되는가?
- [ ] **순서** · 시선 흐름이 과업 순서와 같은가?
- [ ] **신호** · Blue(Primary)·Red(Accent)는 액션/강조에만 썼는가? (장식 금지)
- [ ] **회복** · 에러·빈 상태·취소 경로가 있는가?

하나라도 No면, 컴포넌트를 추가하기 전에 **먼저 줄인다.**

---

## 4. 컴포넌트 절제 규칙

- **새 컴포넌트보다 기존 variant.** 8종(Button·Input·Select·Card·Badge·Tabs·Table·Dialog)으로 먼저 시도한다.
- **variant는 의미가 다를 때만.** 색만 다르면 variant가 아니라 토큰이다.
- **한 화면 Primary CTA 1개.** 두 번째 주 행동이 필요하면 화면을 나눈다(=단계로 분리).
- **칩·배지는 정보 밀도 도구.** 줄글로 충분하면 배지를 쓰지 않는다.

---

## 5. 카피(말) 원칙

- 동사로 말한다: `Ask` `Search` `Share` `Rewrite` · 명사·형용사 CTA 금지.
- 과장 금지: `Oops` `magic` `revolutionary`, 느낌표 남발, 답변 내 이모지 금지.
- 빈 상태는 초대하듯: `Start a thread to see it here.`
- 에러는 행동 가능하게: `Couldn't reach that source. Try again.`
- 근거 없는 확신 금지 · 합성된 주장에는 항상 소스 경로를 붙인다.

---

## 6. 상태(State) · 단계 명확성의 핵심

각 상태는 **고유하고 즉시 식별 가능**해야 한다.

| 상태 | 처리 |
|---|---|
| Empty | 중앙 입력 + 한 줄 안내(`#5c6a6a`), 사과 없음 |
| Loading | Primary shimmer / 뉴트럴 스켈레톤, 최종 치수로 |
| Streaming | 결과가 순서대로 등장 + Primary 커서 |
| Success | 스낵바 Toast(`#303233`) 3초 |
| Error | `#e0524a` 보더 인라인 카드 + 재시도 버튼, 마스코트 없음 |
| Disabled | 40% 불투명, 지오메트리 유지 |
| Focus 활성 | pill → tint 배경 / Primary 보더 |

---

## 7. Do / Don't (요약)

**Do**
- 한 화면 한 결정, 주 CTA 하나
- 사용 순서대로 위→아래 배치
- 상태를 항상 시각화
- 기존 컴포넌트/토큰으로 먼저 해결

**Don't**
- 한 화면에 Primary 버튼 여럿
- 결과(콘텐츠) 위에 부가 설정 배치
- 색만 다른 새 컴포넌트 양산
- 빈 상태/에러를 방치하거나 사과체로

---

## 8. 에셋 원칙 (캐릭터·이미지)

1. **캐릭터는 배경 투명이 필수.** 다음프렌즈 등 캐릭터 SVG/PNG는 **배경 사각형 없이 알파 투명**으로만 사용한다. 어떤 surface(페이퍼·tint·다크·카드) 위에도 자연스럽게 얹혀야 하기 때문.
   - Figma export 시 프레임 배경(`<rect fill="#1E1E1E"/>` 등)이 딸려오면 **반드시 제거**한다.
   - 배경/원형 컨테이너가 필요하면 캐릭터가 아니라 **감싸는 요소**(`ds-persona__avatar`, `ds-personacard__art`)가 책임진다.
2. **캐릭터 색은 그대로, 톤만 절제.** 4색(블루/그린/옐로/레드)은 페르소나 구분 신호 · 임의 리컬러 금지. 단 Blue 액센트와 충돌하지 않게 캐릭터는 일러스트 영역(아바타·카드·빈 상태·처리 화면)에만.
3. **아이콘 우선, 라벨은 호버.** 버튼·상태창은 가능하면 아이콘(`IconButton`)으로 줄이고, 메뉴명은 호버 툴팁(`[data-tip]`)으로 노출해 시각적 군더더기를 줄인다. 단 접근성을 위해 `aria-label`은 항상 유지.

---

## 9. 표기 원칙 (제품 카피)

1. **긴 대시(em-dash, U+2014) 금지.** 제품 UI 카피(라벨·힌트·플레이스홀더·모듈 설명·빈 상태 등)에 긴 대시를 쓰지 않는다. 대신:
   - 구분/병렬: **중점 `·`** (예: `제목 · 부제`)
   - 라벨:값: **콜론 `:`** 또는 중점 (예: `상태: 연결됨`)
   - 부연/예시: **괄호 `( )`** (예: `팀 이름 (예: 콘텐츠검수팀)`)
   - 빈 값 표시: **중점 `·`**
   > 코드 주석·문서도 동일하게 `·` 로 통일한다(일관성). 박스드로잉 `──`(U+2500)은 대시가 아니므로 무관.

## 10. 버튼·액션 원칙 (전 페이지)

1. **맨 텍스트 버튼 금지.** 클릭 액션은 **아이콘 버튼**(범용적으로 자명한 것: 새로고침·닫기·삭제·편집·다운로드) 또는 **박스형 버튼**(면·경계가 있는 `ds-btn`/`.copybtn`)으로만 만든다. `color`·`hover:text-*` 만 있는 링크형 텍스트 버튼은 쓰지 않는다(눈에 안 들어옴).
2. **라벨은 또렷하게.** 버튼 라벨은 Strong 굵기(650+)·음수 자간, 은은한 버튼(secondary·ghost·outline)도 쉼 상태에서 면·경계·미세 그림자로 "버튼임"이 보이게 한다.
3. **카드 안 버튼은 우측 배치.** 헤더/푸터의 액션은 우측 정렬을 원칙으로(타이틀 좌 → 액션 우). 카드 속성(기능/정보 칩+캐릭터)은 종류별로 통일하고 헤드 우측 끝에 고정한다.
4. 아이콘 버튼은 `aria-label` 필수, 의미는 `[data-tip]` 툴팁으로 노출(§8-3과 동일).
5. **공통 버튼 스케일.** 계층=색(`--primary` Blue / `--secondary`·`--outline` 무채 / `--c-danger` Red), 크기=역할: `--s-sm`(28px·12.5px, 인라인·행 액션) · `--s-md`(34px·13.5px, 기본) · `--s-lg`(40px·14.5px, CTA). 모서리 R8 고정. sm 은 semibold(헤비 금지). 인라인 Tailwind 커스텀 버튼 금지 → 반드시 `ds-btn` 계약 사용.

## 11. 탭 · 다크모드

1. **탭은 내용과 연결.** 콘텐츠 전환 탭은 플로팅 필/칩이 아니라 **언더라인 탭**(하단 프라이머리 인디케이터, 콘텐츠 상단에 붙음)으로 "아래 내용과 연결된" 느낌을 준다. (`.evaltabs`)
2. **색은 시맨틱 토큰만(`--ds-*`).** 하드코딩 hex(특히 어두운 골드·화이트 배경)는 다크모드에서 깨진다. 정의 안 된 토큰의 `#fff` 폴백 금지 → `--ds-surface-white` 등 실제 스왑 토큰 사용. 불가피한 강조색은 `[data-theme='dark']` 대비 보정을 함께 둔다.
