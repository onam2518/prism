## 성능 백로그 전량 실행 (#351~#358 · 병행 세션)

행 수가 늘면서 선형으로 느려지던 구간을 한 번에 걷어냈다. 수치 정의는 건드리지 않고
'같은 원본을 몇 번 가져오는가'만 줄인 것이 대부분이다.

- **권한 게이트 왕복**(P1-1 · #351): 위임 관리자 요청 1건이 supabase 를 최대 10회 왕복
  (menu_allowed 6 + 라우트 게이트 4)하던 것을 60s TTL 캐시로 0~2회. 쓰기 경로는 즉시 무효화.
- **핫패스 중복 fetch 제거**(P1-4/5/6 · #353): 같은 요청 안에서 feedback·배정 전량을
  반복 조회하던 것을 1회 조회 + 공유로. /crew 재계산이 약 15회 → 8회 이하.
- **원격 스토어 전량 조회 30s 캐시**(P1-2/3 · #354): `results_rows`(최대 5왕복·수 MB)와
  골든셋 전량을 창 안에서 재사용. `_agg_cached_store` 로 스토어 교체 시 즉시 미스.
- **정적 자산·SPA 재검증**(P1-7/P2-3 · #355): 벤더 자산을 부팅당 1회만 압축 ·
  SPA HTML 은 `ETag=부팅ID` 로 같은 부팅이면 304(135KB 재전송 생략). 새 배포는 ETag 불일치로 갱신.
- **첫 페인트·표 렌더**(P2-4/P2-2 · #356): 앱 조각 15개(약 450KB)에 defer ·
  검수 표 x-for 표시 캡 200 + 더 보기. 건수·필터·일괄 작업은 전체 목록 그대로, 렌더만 절단.
- **/raw 슬림화**(P2-1 · #357 · 최대 임팩트): 목록에서 본문 전문·메타 원본·확신도 재계산을
  빼고 표가 쓰는 평탄 필드만. 2000건 기준 수 MB → 수백 KB. 상세는 `/raw-detail?hash=` 단건.
- **통계 집계 RPC 이관**(P3-1 · #358): `prism_agg_feedback_stats`·`gold_stats`·
  `assignment_load` 신설(운영 적용 완료). 판정 POST 의 feedback 전량 스캔, gold_checks
  최대 2만 행, 배정 분배의 3테이블 전량 전송이 각각 왕복 1회(수 KB jsonb)로.
  함수 미존재 환경은 기존 방식으로 자동 폴백.

⚠ **계약이 바뀐 곳이 있다**: /raw 응답이 슬림해졌고(본문·메타 원본 없음) 상세는 별도
라우트다. 목록 응답에서 body 를 기대하는 코드를 새로 쓰면 조용히 빈 값을 만난다.

## 타임리 라우터 이전 (#362)

스테이징(`router.stg.timelyai.io`)에서 운영(`api.timelyrouter.ai`)으로 옮겼다.
모델 public id 형식(bare)·요청 규격은 그대로라 **주소와 키만** 바뀐다.

- 실호출 확인: `claude-opus-4-8`·`solar-open2` 200 · `max_tokens`/`max_completion_tokens`
  양쪽 수용 · `response_format(json_object)` 동작 · 응답에 `X-Provider` 헤더.
- **`PRISM_TIMELY_BASE` 오버라이드**를 뒀다 — 주소가 또 바뀌거나 되돌려야 할 때 배포 없이
  시크릿만으로 전환한다(키 교체 시점과 주소 전환 시점이 어긋날 수 있다).
- 모델 카탈로그를 `GET /v1/models` 실목록(26종)으로 교체. 신규 `claude-opus-5`·`sonnet-5`·
  `fable-5`·`gpt-5.6` 계열 · **Solar 도 라우터 경유로 쓸 수 있게 됐다**(`solar-pro3`·
  `solar-open2`·`solar-pro2`) · `deepseek-chat` 은 목록에 없어 제거(고르면 404).
- 키가 3종으로 갈려 판별에 시간이 걸렸다. `tgpt_sk_` = TimelyGPT **브리지**용
  (`hello.timelygpt.co.kr/api/v2/chat/bridge/openai` · 모델 id 가 `anthropic/claude-…`
  OpenRouter 형식) · `tk_` = 라우터용. 브리지는 우리가 쓰는 라우터와 **다른 제품**이다.
- 배포 순서: 머지(코드가 새 주소를 봄) → `fly secrets set PRISM_TIMELY_KEY` → 머신 재시작.
  그 사이 401 구간이 생기지만 배치가 안 돌 때 했다.

## 엔티티 확신도 — 가중치를 고치려다 근거가 없다는 결론 (#366)

사용자 지적: "제목 0.55 / 리드문 0.2 인데 둘을 바꿔야 할 듯". 실데이터로 확인했다.

**진짜 문제는 가중치가 아니라 구조적 상한이었다.** 제목을 뺀 합이 0.2+0.1+0.15 = 0.45 라,
리드문·첫문단·본문 반복이 **전부** 걸려도 기본 노출선 0.5 를 넘을 수 없다.

| 구간 | 개수 | 평균 | 최대 | 0.5 이상 |
|---|---|---|---|---|
| 제목에 있음 | 783 | 0.860 | 1.000 | 778 |
| 제목 없음·리드문 있음 | 1,054 | 0.283 | **0.450** | **0** |
| 둘 다 없음 | 835 | 0.064 | 0.250 | **0** |

즉 확신도가 사실상 '제목에 있나?'의 다른 표현이었다.

- `0.55/0.20/0.10/0.15` → **`0.5/0.25/0.15/0.2`**. 제목 밖 합이 0.6 이 되어 리드문에 더해
  **원문 근거(첫문단·반복)가 받쳐줄 때만** 통과한다(리드문에만 스치면 0.25 로 접힘).
- 제목 0.55 는 근거가 약했다: 실측 실개체율이 제목 있음 36% · 리드문만 30%.
- **리드문을 제목보다 올리지는 않았다** — 리드문은 우리 모델이 엔티티 목록과 **같은 호출에서
  만든 산출물**이라 자기참조다. 제목은 원문 사실이다.
- 운영 실측: 기본 노출 **791 → 948(+157)**. 되살아난 예 — `이상혁`(제목엔 별명 '페이커'만
  있어 가려졌다) · `PSAT`·`통계학`(합격 수기) · `사크레쾨르 대성당`(몽마르트 기사).

**⚠ 판별력은 오르지 않았다.** 어떤 조합을 써도 AUC 0.610~0.615 로 평평했다(대리 정답 =
사전 타입 확정 여부). 바뀌는 것은 0.5 선의 위치뿐이다.

| 조합 | AUC | 정밀도 | 재현율 | 통과 |
|---|---|---|---|---|
| 기존 | 0.610 | 0.33 | 0.39 | 570 |
| 제목↔리드 스왑 | 0.615 | 0.29 | 0.69 | 1,133 |
| 적용값 | 0.611 | 0.34 | 0.47 | 676 |

## 엔티티 관련성 라벨 수집 (#367)

가중치 최적화가 의미를 가지려면 정답이 필요한데 쓸 수 있는 신호가 둘 다 안 됐다.

- 검수 교정 기록(`patch_log`): **5건뿐이고 전부 추가** — 삭제 사례가 0.
- 엔티티 사전 상태: '실존 개체인가'를 잴 뿐 '이 기사에서 중요한가'가 아니다.

그래서 `prism/entlabel.py` 를 만들어 직접 받는다.

- 수집 지점은 상세의 **'연관 낮음'** 영역. 거기 접힌 것이 정확히 경계선 표본이라 판별력을
  올리는 데 값어치가 가장 크다(불확실 구간 우선 라벨링).
- **콘텐츠를 바꾸지 않는다** — 엔티티 삭제는 정답셋에 반영되는 무거운 결정이라 잘 안 누르지만
  (실측 5건), 라벨은 답만 남아 부담이 없다. 편집 UI 에 삭제가 이미 있는데도 안 쌓인 이유다.
- 검수자별 1표(재클릭 = 취소) → 합의율 측정 가능 · 내보내기는 **합의된 표본만**.
- 전체 검수자·최종검수자 모두 참여(`gate=login`). 접두가 `/entity` 라 메뉴 권한에 안 걸리는
  것을 테스트로 고정했다(#343 과 같은 사고 방지).
