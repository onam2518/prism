## 발단 — 새 기준과, 그것을 판정할 재료의 부재

운영파트 합의안: **단순 정량(포토 n장 이상) 금지 · 직접 촬영한 사진 · 현장 취재 성격**.
부여 O 12건 / 미부여 X 10건의 실제 기사 URL 을 글자수·이미지 수와 함께 제시.

조사 결과 세 겹으로 막혀 있었다.

**① 인텐트 호출만 본문에서 끊겨 있다.** `meta_prompts.call_user` 를 보면 리드문·엔티티·
카테고리 호출은 전부 `body` 를 받는데 인텐트만 `displayServiceName` + 리드문 1문장이었다.

```python
if call == "intent":
    return f"displayServiceName: {dsn}\nsummary: {prior.get('summary', '')}"
```

합의안이 사례마다 병기한 글자수 121~5,568자, 이미지 1~10장이 판단 재료에 도달하지 않는다.
`[오늘의 1면 사진]` 처럼 **제목이 판정을 가르는** 사례도 제목조차 안 들어갔다.

**② 사진이 모델에 도달하지 않는다.** `schema.py` 주석이 `image_urls` 를 "참조용 · 추출 입력
아님" 으로 못 박고 있다. 비전 호출 경로는 있지만 실험실 미디어 탭 한 곳뿐이고 `persist=False`.

**③ 판별 신호가 없다.** 사진 크레딧(`ⓒ연합뉴스`·`○○ 제공`)을 읽는 코드가 저장소 전체에
0건. 비전 스키마는 `description`·`visible_text`·`entities`·`scene` 4종뿐이라 사진 종류나
촬영 주체를 묻는 항목이 없다.

**④ 정의문을 고쳐도 모델은 안 바뀐다.** `intent_dictionary_text()` 가 범용②는 값 이름만
넣고 설명 병기는 서비스 분기값에만 한다. `INTENT_VALUE_DEFS` 수정은 검수 UI 호버만 바꾼다.

**⑤ 현행 규칙은 부호가 양방향으로 뒤집힌다.** "캡션이 본문과 직접 연관될 때만 부여"
(260715 회의)를 합의안 사례에 적용하면 팩트체크는 **오부여**, `[오늘의 1면 사진]`(122자)은
**누락**된다. "많더라도" 라는 정량 프레이밍이 1장 케이스를 규칙 밖에 둔다.

운영 실측(Supabase 400건)으로 확인한 것: 영문 기사 **0건** · `image_urls` 채워진 행 **0건** ·
`service='포토'` **0건** · `content_track` 은 운영 DB 에 컬럼 자체가 없음.

## 이미지 URL 유실 — 상류 문제가 아니라 우리 버그였다 (#378)

운영 400건 전부 `image_urls` 가 빈 목록이었다. 처음엔 상류가 안 보내는 것으로 의심했는데,
추적해 보니 3단 인과가 전부 우리 코드였다.

1. `supastore.sync_contents` 는 행을 `out["content_ref"]` 가 아니라 **`content` dict** 에서
   만들고 `image_urls` 를 항상 payload 에 싣는다. `_upsert` 가 `merge-duplicates` 라
   **`content` 에 이미지가 없으면 기존 행이 `[]` 로 덮인다.**
2. `runops.rerun_content` 가 `content_ref` 로 입력을 되만들 때 `source_url` 만 보존하고
   `image_urls` 를 빠뜨렸다.
3. 운영 플로우가 정확히 이 경로다. STEP 1 추가(이미지 보존됨) → STEP 2 실행 =
   `rerun_all(scope="pending")` → `rerun_content` → 이미지 삭제 + `source='재실행'`.
   **400건이 전부 `source='재실행'` 인 관측과 정확히 일치**한다.

부수 발견: 단건 `/run` 도 항상 유실 · `/run?add_only=1` 은 `serve._p_run` 화이트리스트에
`image_urls` 자체가 없었음 · sqlite 모드도 동일. 엑셀 배치·자동 인입만 정상이었다.

저장 계층은 건드리지 않았다. `sync_contents` 의 계약 자체는 정상(`source_url` 도 같은 규약)이고
잘못은 호출자 쪽이었다. 회귀 14건 추가 후 수정 전으로 되돌려 **9건 실패**를 확인했다.

관측 수단도 붙였다. 실행 큐 메시지 끝에 `· 이미지 3/50건` 을 덧붙여, 배포 후 첫 인입에서
**상류 미전송인지 우리 누락인지** 화면에서 바로 갈리게 했다.

기존 400건은 값이 지워진 뒤라 소급 복구 불가.

## 사전 오버라이드가 신규 값을 영구 차단하고 있었다 (#373)

`apply_profile` 이 리스트를 병합이 아니라 **통째 재바인딩**한다.

```python
if isinstance(cur, dict) and isinstance(prof[pk], dict):
    cur.update(prof[pk])
else:
    g[gk] = prof[pk]      # list 는 여기 — 통째 덮어쓰기
```

**사람의 실수가 아니라 설계 결함이다.** 로컬 `dict_overrides.json` 은 07-06 관리자 UI 편집
산출물이고 당시 범용①은 8종이 맞았다. 이틀 뒤 `f391b8d`(07-08)로 관점 축 `옹호·지지`·
`반박·비판` 이 추가됐지만 8종 스냅샷이 그대로 붙들고 있다. **사전 편집을 한 번이라도 쓴
인스턴스는 그 이후의 모든 사전 확장을 못 받는다.**

격리 실행으로 실증:

```
BEFORE  n=10  [..., '옹호·지지', '반박·비판']
AFTER   n=8   LOST: ['옹호·지지', '반박·비판']
verify_item(['반박·비판','심층 분석']) → ['심층 분석']   notes=['intent 사전외 제거: 반박·비판']
```

가장 나쁜 건 **프롬프트가 자기모순 상태**가 된다는 것. 값 목록은 8종으로 줄지만 바로 아래
경계 지침("한쪽 논조가 뚜렷하면 옹호·지지 … 반박·비판을 우선한다")은 하드코딩이라 잔존한다.
목록에 없는 값을 우선 부여하라고 지시하면서 동시에 "목록 내에서만 선택"을 요구한다.

게다가 검수 UI 는 `intentDefs` 로 정의를 그대로 노출하므로 **정상으로 보인다**. 검수자는
"옹호·지지가 있는데 왜 한 번도 안 붙지?" 만 관측하게 된다. 회귀 테스트 가드도 0이었다
(관련 테스트가 오버라이드 미적용 상태만 검사).

수정: 리스트를 **병합 + 삭제는 툼스톤(`_removed`)으로 명시 기록**. `edit_dict` 가 저장 직전
"이번 편집이 코드 기본값에서 뺀 값"을 남긴다. 툼스톤 없는 구형 파일은 (a)의도적 삭제와
(b)코드 신규 추가를 원리적으로 구분할 수 없어 **무손실 쪽(합집합)** 을 택했고, 무엇이
복원됐는지 기동 로그로 안내한다. 무음 `except: pass` 도 제거.

**운영 확인**: `GET /dict` 의 `intentUniversal` 이 10종인지. 8종이면 관점 축 소실.

## 인텐트 정확도 지표 · 회귀 가드 (#377)

기준을 바꿔도 **좋아졌는지 답할 수단이 없었다**. 채점은 `finalGrade` 와 `reasons` 만 보고,
`expected["intent"]` 는 골든에 저장만 되고 어떤 지표에도 반영되지 않았다. 회귀 가드 3종
(`_batch_regressions` · 학습 배치 자동 원복 · `eval_run_compare`)이 전부 침묵한다.

- `intent_exact` · `intent_jaccard` · `intent_top1` · `by_intent_value`(값별 P/R/F1) 신설.
  `abtest.score`(일괄)와 `evalops._tally`(증분)가 같은 카운터를 쌓고 같은 리포트 함수를
  공유하도록 묶고 패리티 테스트로 고정.
- **순서는 집합 의미로**. LLM 경로는 응답 순서를 보존하지만 임베딩 경로는 코사인 랭킹으로
  재배열되고 `merge_perspective` 가 관점 축을 뒤에 덧붙인다. 순서를 지표로 쓰면 방법론 교체만
  으로 흔들린다. 대표값만 `intent_top1` 로 분리.
- **표본은 기대 라벨이 1개 이상인 행만**. `build_golden_from_reviews` 가 검수 유래 골든 전건에
  intent 키를 무조건 써넣어 키 유무로 라벨 유무를 못 가리고, R 등급 행은 harness 가
  `item_meta` 를 억제해 기대·산출이 모두 공집합인 자동 만점 행이 된다. 제외 건수는
  `intent_skipped` 로 노출.
- 회귀 임계: 자카드 **5%p 초과 악화 · 표본 20건 이상**(n=20 에서 한 건 뒤집힘이 1/n=5%p 를
  움직이므로 단일 건이 단독으로 가드를 넘기지 못하는 최소 조합) · 값별 F1 **10%p 초과 하락 ·
  support 5 이상**(기존 버킷 가드와 동일 임계). `intent_exact` 는 고분산이라 리포트만.
- `register_golden` 이 `intent` 를 검증 없이 통과시키던 것도 화이트리스트 정제로 수정.

**배포 후 `intent_n` 확인 필요.** 20건 미만이면 가드가 아직 잠들어 있다는 뜻이다.

## 그 밖

**본문 HTML 정제 (#379)** — 티스토리·다음카페 본문에 마크업·CSS 가 그대로 적재돼 있었다
(최악: 49,039자 중 라틴 33,311자·한글 1,895자). `schema.py` 정규화에 화이트리스트 방식
strip 추가. 해시는 원본 dict 로 계산되므로(`store.content_hash`) **정체성 불변** — 기존
400건 복제 없음. 작업 중 두 가지를 잡았다: 평문 `a<b 이고 b>c` 를 태그로 오인해 문장을
잘라먹던 것, 속성부 이중 별표가 `<div`+공백 2만자에서 **539ms(O(n²))** 걸리던 DoS 벡터
(0.35ms 로 수정). 곁다리로 `fewshot.py` 가 골든 본문을 정제 없이 180자로 잘라 few-shot
예시가 마크업뿐이던 것도 고쳤다.

**인입 라벨 보존 (#374)** — 400건 전부 `source='재실행'`. `source` 를 "최초 인입 1회 기록"
으로 확정. 별도 컬럼을 안 쓴 이유: Supabase DDL 은 코드로 적용되지 않아 컬럼을 보내는 코드가
먼저 배포되면 DDL 적용 전까지 upsert 가 전량 실패(PGRST204)한다. PostgREST `merge-duplicates`
가 조건부 갱신을 표현 못 해 쓰기 직전 기존 라벨을 읽어 되돌려 보내는 방식으로 처리.
발견: `source='image'` 는 **애초에 DB 에 기록된 적이 없다** — `runops` 의 그 값은 응답 JSON
표기용이고 적재는 기본값 `단건` 으로 호출된다.

**인텐트 라벨 위생 (#375)** — 폐기 라벨이 `topic.py`·`memfs.py`·`app-11-contentagent.js`
3곳에 하드코딩. 전부 **저장된 과거 데이터를 읽는 경로**라 단순 삭제가 불가능해 현행/레거시로
분리했다. `memfs.INT_KO` 는 10개 중 현행이 2개뿐이라 데모 카탈로그·검색 칩이 사실상 비어
있던 실버그였다. 핸드오프 번들에 범용② 8종과 정의문이 통째로 빠져 있던 것도 동봉.
`displayServiceName="포토"` 는 조사 결과 **누락이 아니라 의도**(트랙 표식 · 서비스 미상 입력의
PGC 폴백이 설계된 정답)로 판단해 매핑은 건드리지 않고 주석만 남겼다.

**설계 문서 (#383)** — `docs/IMAGE_META_DESIGN.md`. 이미지 반영 계획이 아직 없어 설계만.
URL fetch 안전 규칙(SSRF·크기 상한·리다이렉트 재검사) · 비전 스키마 확장 5항목 · 저장 위치의
Supabase DDL 순서 함정 · 비용 계상 · 단계 0~4. 결론 하나: **별도 크레딧 파서는 불필요**.
번인된 `ⓒ연합뉴스` 는 이미 `visible_text` 로 읽히므로 스키마에 `credit_text` 항목 하나만
추가하면 된다.

## 운영파트 회신과 확정된 결정

회신 후 네 가지가 확정됐다.

1. **260715 회의 결정 폐기** — 운영 합의가 앞선다.
2. **인텐트로 유지** — 별도 편성 스코어/플래그로 빼자는 대안 기각.

4. **최종 방향은 이미지 메타 추출 반영** — 단 착수 시점 미정, 설계만.

현장 사진이 섞이는 문제로 오판이 크다. 더 고민이 필요하다.
