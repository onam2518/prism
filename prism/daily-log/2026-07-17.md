## 진척율·퀘스트 모집단 정합 (#213)

- **증상**: 퀘스트 생성 직후 검수 0건인데 `팀 평균 4/4 · 100% · ✓ 완주` · 홈 히어로
  `검수 대상 4건 중 내가 45건 검수 · 0%`(성립 불가 문장).
- **원인**: 분자·분모가 서로 다른 모집단. 분모는 현재 YELLOW(4건)인데 퀘스트 분자는
  전 기간 피드백 전체(이미 확정·삭제된 콘텐츠 포함 · 초안 시각 미상은 무조건 유효
  취급) → 과거 실적으로 즉시 4/4 클램프. 히어로 캡션의 "내가 N건"은 누적 reviews
  (점수 원천), %는 배정 기준 — 세 숫자가 제각각.
- **수정**: `yellow_hashes()` 공통 모집단 도입, 분자를 현재 대상으로 스코프.
  리더보드에 `target_reviews`/`assigned_total`/`assigned_done` 노출, 캡션을 진척율과
  같은 모집단으로(배정 있으면 "내 담당 N건 중 M건"). 누적 reviews 는 점수용으로 유지.
- 기존 스모크(test_09)가 **삭제된 콘텐츠의 고아 피드백** 덕에 통과하고 있었음이
  드러남(= 제보된 버그가 테스트의 통과 조건). 살아있는 YELLOW 검수 시나리오로 재작성.

## '100건 배정이 96건' — PostgREST 행 클램프 (#216)

- **실측(운영 supabase)**: PostgREST 는 **요청 limit 과 무관하게 서버 max-rows(1000)로
  응답을 클램프**한다 — `limit=50000` 요청 → 1000행, 무 limit → 1000행, offset 페이징은
  정상. 배정 테이블 1018행(고아 122행 포함) 중 **ts 순 최신 18행이 조용히 유실** →
  절대자 99→96 · 애쉬/해씨/에디 99→97 표기. 시뮬레이션이 화면 수치와 정확히 일치.
- `_all_feedback` 의 `limit=50000` 명시 상한도 같은 이유로 사실상 1000 캡이었다 —
  피드백 333행이 이번 배정분 검수(~900건)로 곧 1000을 넘는 시한폭탄까지 선제 해소.
- **수정 4종**:
  - `supastore._get` 을 offset 페이지네이션으로 전환(PK 안정 정렬 `_PAGE_ORDER` 자동
    부여 · `limit=` 은 '호출자 상한'으로 해석해 그 수까지 수집).
  - 고아 배정 차단: `clear_team_contents` 배정 연쇄 삭제(양 스토어) + arena '내 담당'·
    팀 진척·`assignment_load`(균등 분배 가중)에서 삭제된 콘텐츠 배정 제외.
  - **검수 대상 재정의**: `review_targets()` = 현재 YELLOW ∪ 배정된 살아있는 콘텐츠.
    일괄 배정 운영은 auto 콘텐츠도 배정해 검수시키므로 "검수 대상 4건"(YELLOW만)이
    팀 목표(199건)와 어긋나던 정의 문제 해소. 퀘스트·홈 진척 분모 일원화.
  - 랜덤 추출이 풀 부족으로 요청보다 적게 뽑히면 경고 배지("요청 N건 중 M건만") ·
    배정 모달 풀 상한 200→1000. (그룹2가 99건이 된 원인 = 조용한 축소)
- **운영 조치**: 고아 배정 122행 1회 정리(1018→896행 · 고아 0) — 1000행 아래로
  내려가 구 배포본에서도 배정 수 즉시 정상화.

## 운영 메모

- **supabase 대량 조회는 반드시 `supastore._get` 경유**(페이지네이션 내장). 명시
  limit 도 서버 캡을 못 넘으니 직접 `_req` GET 을 만들지 말 것. 새 테이블은
  `_PAGE_ORDER` 에 PK 등록.
- 검수 대상의 단일 정의는 `review_targets()`(YELLOW ∪ 배정∩생존) — YELLOW 단독
  분모로 되돌리지 말 것. 콘텐츠 삭제 경로는 배정 연쇄 삭제가 계약.
- 원인 조사에 운영 DB 직접 조회(read-only)가 결정적이었다 — 화면 수치(96·97)와 행
  클램프 시뮬레이션의 일치로 원인을 확정. 파괴적 정리(DELETE)는 사용자 승인 후 실행.
