# 발행 메타 수집기 설계 · 사내망 수집 → 프리즘 검수 지정

작성 2026-09-02. 기획 원본은 DNM 위키 Prism 페이지(395280444) "기획 · 콘텐츠 조회 → 검수 지정" 섹션.
구현 선행분은 `prism/metaquery.py`(PR#495 · v1.406). 이 문서는 그 뒤에 결정된 **수집 환경**을 적는다.

## 1. 결정 사항 (2026-09-02)

| 항목 | 결정 |
|---|---|
| 수집 환경 | STATUS AGENT 저장소(`~/Desktop/status-agent` · 오르카 프로젝트 폴더)의 엔진을 쓴다. bi-portal 메타베이스는 사내망(VPN) 전용이라 fly.io 의 프리즘 서버가 직접 조회할 수 없다. |
| 소스 | 데브가 **별도 테이블**을 조회 가능하게 노출한다. 유니크 키와 프리즘 구성에 필요한 부수 항목만 담는다. |
| 메타 본체 | 요약·엔티티·의도·카테고리 등 발행 메타는 **인퍼럴 메타 DB** 에만 넣는다(추가 예정 · 아직 없음). |
| 목표 | 프리즘 내재화. 수집 코드는 프리즘 저장소가 소유하고, 실행만 사내망에서 한다. |
| 배치 주기 | 6시간 간격 하루 4회(2026-09-02 확정 · 3절 배치 정책). 실시간 불필요 · 부하 분산 목적. |

## 2. 구조 (2026-09-02 수정 · 스테이징 도입)

원안은 "조회 화면에서 보고 고른 것만 검수로 지정"이다. 수집기가 지정(register)을 직접 부르면 그 고르는
단계가 사라지므로, 수집기는 **조회 결과를 스테이징에 올리기만** 하고 지정은 화면에서 한다.

```
[사내망 · 수집기]                                            [fly.io · 프리즘 운영]
개인 bi-portal 세션 토큰(~/.cache/slate_mb_token)
  1) 발행 테이블 조회  (증분: 마지막 수집 시각·키 이후)
  2) item 소스(db52)에서 본문·부제·URL 보강 (키 IN 목록 · date_id 필터)
  3) 인퍼럴 메타 DB 조인 (추가 예정)
  4) metaquery.COLUMNS 별칭으로 rows JSON 조립
  5) POST /metaquery-stage  ── 관리자 Bearer ──▶  스테이징(mq_stage · 검수 콘텐츠 아님)
  6) 상태 파일 갱신(마지막 키·시각) · perf.jsonl 기록          │ 운영자가 조회 화면에서 확인·선택
                                                               ▼
                                              검수 지정(/metaquery-register · 기존 그대로)
                                              나머지: 선택 삭제 또는 7일 뒤 자동 정리
```

- 스테이징은 results 와 분리된 표(SQLite `mq_stage` · 수파베이스 `prism_mq_stage`). 보존 90일 대상이 아니다.
- 조회 화면 기본 소스 = 스테이징. 서버 직접 조회(source=metabase)는 사내망에서 프리즘을 띄운 경우에만 쓴다.
- 같은 콘텐츠를 다시 올리면 최신 행으로 덮는다(발행 메타 갱신 반영). 지정된 콘텐츠는 "인입됨"으로 표시된다.
- 실데이터 검증은 스테이징에 올려 화면에서 확인한 뒤 삭제하면 된다. 검수 큐에는 아무것도 들어가지 않는다.

바뀌지 않는 것: `/metaquery-register` 계약 · 중복 방지(`existing_hashes`) · `purpose=eval` 처리.

## 3. 단계

### 1단계 · 수집 스크립트 (STATUS AGENT 엔진 위)

- 위치: `status-agent/prism_push.py`(뼈대 작성 2026-09-02 · status-agent PR#1). `prism_contents.py`(분류별 후보 xlsx)와 같은 자리.
- 조회는 전부 `slate_query.run_sql`(린터 · 40초 게이트 · 조각 캐시 · perf 로그)을 거친다. AGENTS.md 절대 규칙 2 준수.
- 인증 두 개: bi-portal 은 `login.py` 로 받은 개인 토큰, 프리즘은 실행자의 관리자 로그인 토큰(env `PRISM_TOKEN`).
  서버에 상시 자격 증명을 두지 않는다.
- 기본 POST 대상은 `/metaquery-stage`(스테이징). `--register` 를 주면 화면을 거치지 않고 바로 지정한다(메타 DB 이후 자동화 단계용).
- 회당 200건 상한(`metaquery._LIMIT_MAX`)이라 그 단위로 POST 를 나눈다.
- 출력: 추가 n · 기존 m · 비어서 건너뜀 k. 실패 시 상태 파일을 갱신하지 않아 다음 회차에 다시 잡는다.

### 2단계 · 프리즘 내재화

- 위치: `prism/metacollect.py`. 표준 라이브러리만(urllib · json · sqlite3). 서버(`serve.py`)는 건드리지 않는다.
- 엔진 규칙을 코드로 고정한다: SQL 은 고정 템플릿(열 명시 · `date_id` 파티션 필터 · 행 상한 · 60초 타임아웃).
  린터가 막는 형태가 나올 수 없게 만들어 별도 린터 없이 같은 규율을 지킨다.
- 세션 토큰은 같은 파일(`~/.cache/slate_mb_token`)을 읽어 status-agent 와 로그인 한 번으로 공유한다.
- 실행: `python3 -m prism.metacollect --since <시각>` 을 사내망 호스트의 cron/launchd 에 건다.
- 1단계 스크립트는 2단계가 안정되면 삭제한다. 두 개를 병행 운영하지 않는다.

### 배치 정책 (2026-09-02 확정)

| 항목 | 값 |
|---|---|
| 주기 | 6시간 간격 하루 4회 (00 · 06 · 12 · 18시 KST) |
| 범위 | 직전 회차 이후 발행분 + 앞뒤 1시간 겹침(같은 콘텐츠는 덮어쓰기라 안전) |
| 회당 규모 | 하루 3.5만 건 기준 약 9천 건 · 200건씩 나눠 스테이징 POST · 예상 3~5분 |
| 조회 화면 | 필터를 먼저 고르고 조회 · 발행 기간 기본은 오늘 하루(기간 지정 가능) · 50건 페이지 넘김(부담 분산) |
| 정리 | 지정 안 한 행은 7일 뒤 자동 삭제 (전량 스테이징이면 약 1GB 상주 · 필요 시 3일로 단축) |
| 하한 | 1시간(토큰 갱신 · 조각 게이트 · 검수 속도에 이득 없음) |

실시간성은 요구하지 않는다. 하루 1회 대신 4회로 나눈 이유는 bi-portal 조회량과 프리즘 DB 쓰기를 한 덩어리로
몰지 않기 위해서다. 회당 소요가 5분을 넘으면 4시간 6회로 내린다.

| 지표 | 출처 | 조정 |
|---|---|---|
| 회당 소요 | perf.jsonl · 수집기 로그 | 40초 게이트에 걸리면 기간을 나누거나 키 IN 목록을 줄인다 |
| 회당 행수 | stage 응답 added/updated | 200건 분할 횟수가 늘면 4시간 6회로 |
| 프리즘 부담 | fly 로그 57014(statement timeout) 재발 | 재발하면 주기를 늘리거나 회당 건수를 줄인다 |

## 4. 데이터 계약

### 발행 테이블(데브 노출) · 필요한 열

| 열 | 용도 | 비고 |
|---|---|---|
| 유니크 키 | 중복 방지 · item 소스 조인 · trace.source_id | 이름·형식 미정(iuk 인지 별도 id 인지) |
| service | displayServiceName | 서비스 코드면 이름 매핑 필요 |
| published_at | 증분 수집 기준 | 파티션 열이 따로 있으면 그 열도 |
| model · version | trace.model("dev:" 접두) · trace.version | 없으면 "metabase" · 배치 번호 +1 |
| grade | quality_meta.finalGrade | G/R 만 반영 |

본문·부제·URL 은 이 테이블에 없어도 된다. item 소스에서 키로 보강한다.

### 인퍼럴 메타 DB(추가 예정) · 조인 열

summary · entities · intent · category. 키로 조인해 `item_meta` 를 채운다.

### 주의 · 메타 DB 가 붙기 전 기간

`mq_register` 는 발행 메타가 전혀 없는 행(item_meta 비어 있고 grade 도 없음)을 **초안이 아니라고 보고 건너뛴다**.
인퍼럴 메타 DB 가 붙기 전에는 발행 테이블에 grade 라도 있어야 인입된다.
grade 도 없다면 선택지는 둘이다. (a) 메타 DB 가 붙을 때까지 수집을 시작하지 않는다.
(b) 메타 없는 초안 인입을 허용하는 스위치를 register 에 추가한다. 이 경우 STEP 2 가 재추출하므로
"재추출 없음" 원칙을 깨는 예외가 된다. **2026-09-02 (a) 로 결정.** 그 전까지는 `--dry-run`·로컬 프리즘으로 경로만 검증한다.

3. ~~메타 없는 기간 처리~~ → 2026-09-02 결정: (a) 인퍼럴 메타 DB 가 붙은 뒤에 수집을 시작한다. register 에 메타 없는 초안 스위치는 만들지 않는다.
4. ~~실행 호스트~~ → 2026-09-02 결정: 당분간 사용자 본인 맥(VPN · status-agent 실행 환경)에서 에이전트가 수동 실행. 주기가 짧아지면 launchd·사내 서버 검토.

6. DNM 위키 기획 섹션 "미확정 사항"에 수집 환경 결정 반영(이 세션에서는 위키 편집 도구가 없어 미반영).
